# VolunteerFlow 阶段 4D：真实双实例部署与 k6 压测设计

## 1. 目标与边界

阶段 4D 在真实虚拟机环境中验证阶段 4B、4C 的运行态能力，不新增业务功能。
本阶段必须形成可以复现的证据，证明：

- 两个 Spring Boot 实例经 Nginx 对外提供同一个入口；
- 两个实例共享 Redis 限流状态；
- 100 个独立成员竞争 20 个名额时不超卖、不重复报名，候补序号不重复；
- Redis 不可用时，业务限流按既定策略放行，MySQL 仍保证报名正确性；
- Redis 恢复后，全局限流和普通业务请求恢复正常；
- 本次测试数据可以按运行标识精确清理，不影响既有业务数据。

阶段 4D 不承诺生产容量，不设置未经业务依据确认的延迟 SLA。吞吐量、延迟和错误率
只记录本次真实测试结果。由于 k6 与被测服务运行在同一台虚拟机，性能数据只能表述为
“单机部署、单机发压基线”，不能表述为独立压测机或生产环境容量。

## 2. 已确认环境与安全约束

- 目标虚拟机：`192.168.40.144`，SSH 端口 `22`，用户 `root`；
- MySQL：虚拟机已有 Docker 容器，对应用暴露端口 `3307`；
- Redis：虚拟机已有 Docker 容器，对应用暴露端口 `6379`；
- 恢复数据库继续使用 `SPRING_FLYWAY_ENABLED=false`，不得删除、修改或伪造
  `flyway_schema_history`；
- 不停止、删除或重建现有 MySQL 和 Redis 容器；
- 不修改用户现有的 MySQL、Redis 地址和端口；
- 不执行全库清空、数据库重建或无法按运行标识限定范围的清理；
- 不在 Git、命令行参数、日志或报告中保存 SSH 密码、数据库密码、JWT 密钥、
  限流 HMAC 密钥等秘密。

SSH 使用一次性密钥完成自动化。用户只在可见终端中输入一次 root 密码，将带唯一注释的
临时公钥追加到 `authorized_keys`。测试结束后必须按完整公钥内容精确移除该行，并删除本地
临时私钥；不得覆盖整个 `authorized_keys` 文件。

## 3. 部署架构

阶段 4D 使用显式双实例部署，不使用 `docker compose --scale`：

```text
k6 容器
   |
   v
Nginx :8088
   |-------------------|
   v                   v
backend-a :8080     backend-b :8080
   |                   |
   |------ MySQL -------|
   |------ Redis -------|
```

Compose 覆盖文件声明 `backend-a`、`backend-b` 两个配置相同、名称稳定的后端服务。
Nginx upstream 显式包含两个实例并进行轮询。Nginx 访问日志记录上游地址、响应状态、
请求耗时和上游耗时，以便证明请求确实经过两个实例；这些日志不得包含 Authorization、
Cookie、请求体或其他秘密。

两个后端实例使用相同的数据库、Redis database、JWT 密钥、限流 HMAC 密钥和限流策略。
后端端口不映射到宿主机，对外只暴露 Nginx。readiness 继续只反映应用和数据库就绪状态，
Redis 故障不能让整个服务失去就绪状态。

源码上传到虚拟机独立目录 `/opt/volunteerflow-stage4d/<runId>`。部署不得覆盖现有项目目录、
Compose project 或容器。Compose project name、容器、网络和测试数据都包含同一个 `runId`，
从而支持精确定位和回收。

## 4. 测试数据与令牌

阶段 4D 新增专用数据夹具，提供 `seed`、`verify`、`cleanup` 三种动作：

- `seed` 创建带唯一 `runId` 的组织、活动、容量为 20 的先到先得岗位和 100 个模拟成员；
- 正常 Redis 场景和 Redis 故障场景使用不同的数据集标识，避免互相污染；
- 模拟账号不使用真实姓名、学号或联系方式；
- 夹具使用与部署相同的 JWT 密钥为 100 个模拟成员生成短期访问令牌文件，避免为了准备
  报名压测而突破登录 IP 限流；
- 令牌文件属于敏感临时产物，只保存在权限受限的运行目录，不进入 Git，测试完成后删除；
- `verify` 直接读取 MySQL 最终事实，不能只根据 HTTP 响应推断正确性；
- `cleanup` 只删除能够追溯到该 `runId` 的数据，并在删除后验证该运行的数据归零。

测试前记录既有业务数据的表级计数和稳定指纹；清理后再次计算并比较。夹具必须使用明确的
运行前缀和关系链，不能依赖“最近创建的数据”或宽泛时间范围进行删除。如果测试失败，先
保留现场并复制证据，之后再执行精确清理。

## 5. 压测与故障场景

### 5.1 预检与双实例分流

远程执行前检查 Docker Engine、Docker Compose、磁盘空间、端口占用、现有容器、MySQL
连通性、Redis 连通性、数据库结构和 Flyway 状态。任一关键预检失败时停止执行，不自动修改
虚拟机基础环境。

部署完成后先检查两个后端实例的 readiness，再通过 Nginx 发出一组无副作用请求。验收日志
必须同时出现 `backend-a` 和 `backend-b` 的上游记录。

### 5.2 跨实例 Redis 限流

本次运行生成独立的 `RATE_LIMIT_KEY_SECRET`，避免与历史限流键相互影响。k6 从同一客户端
地址快速发送超过登录 IP 限额的请求，并使用自定义检查区分认证失败和限流拒绝。

验收要求：两个后端实例合计只放行一份配置额度，超出部分返回 `429` 和合法的
`Retry-After`，不能出现每个实例各自拥有一份 Redis 额度的情况。同时通过 Nginx 日志证明
请求到达过两个实例。

### 5.3 Redis 正常时的并发报名

k6 使用 100 个独立 JWT，在同步起跑点后各提交一次报名，请求同一个容量为 20 的岗位。
所有业务请求都经过 Nginx。HTTP 层记录状态和耗时，完成后由数据夹具检查 MySQL。

硬性验收结果：

- `CONFIRMED` 恰好 20 条；
- `WAITLISTED` 恰好 80 条；
- 100 个成员各自只有一条有效报名关系和一个本轮有效周期；
- 候补序号恰好覆盖 1 至 80，不重复、不缺失；
- 岗位的下一个候补序号与实际分配结果一致；
- 不出现被限流、未认证或服务器错误导致的遗漏请求。

### 5.4 Redis 故障时的并发报名

不停止现有 Redis 容器。通过阶段 4D Compose 覆盖参数，重建两个后端并让其连接一个明确
不可达的 Redis 地址；MySQL、JWT 和其他配置保持不变。使用另一组独立的 100 人、20 名额
夹具重复并发报名。

业务限流遇到明确的 Redis 存储不可用异常时应放行，最终 MySQL 事实仍必须满足 20 条
`CONFIRMED`、80 条 `WAITLISTED`、无重复报名和候补序号完整。登录降级另用少量请求验证
两个进程各自启用容量受限的本机计数器；报告必须明确说明它不是跨实例全局限流。

动态二维码凭证依赖 Redis，其故障语义仍是 `503 DYNAMIC_CHECKIN_UNAVAILABLE`，不能被
业务限流的 fail-open 结论覆盖。

### 5.5 恢复

将两个后端恢复为真实 Redis 地址，等待 readiness 后重新执行 Redis 限流小样本、普通活动
读取和报名状态读取。只有这些检查通过，才能判定恢复成功。

## 6. 指标、判定与报告

k6 脚本为每个场景定义业务检查和阈值：正确性检查必须全部通过；预期出现的 `401`、`429`
或 `503` 由场景专用指标判断，不能混入普通成功率。并发报名场景将非预期 HTTP 状态、网络
错误或缺失响应视为失败。

报告至少记录：

- 执行时间、Git commit、`runId` 和脱敏后的部署参数；
- 虚拟机 CPU、内存和 Docker 版本等基础信息；
- k6 的请求数、吞吐量、p50、p90、p95、p99、最大延迟和错误率；
- 双实例命中证据及共享限流判定；
- 正常 Redis 和 Redis 故障场景的数据库终态；
- 恢复检查结果；
- 清理前后既有数据指纹对比；
- 失败项、限制和不能外推的结论。

小型汇总 JSON、Markdown 报告和必要的脱敏日志片段进入 Git。体积较大的 k6 原始输出、完整
容器日志、令牌文件和真实 `.env` 放入被 `.gitignore` 排除的本地验收目录。任何用户数、
延迟、吞吐量和错误率都必须来自本次真实运行，不预填示例结果。

## 7. 自动化与可维护性

仓库新增以下组件：

- 阶段 4D Compose 覆盖文件和双实例 Nginx 配置；
- 可按 `runId` 操作的数据夹具；
- k6 双实例限流、正常报名、Redis 故障报名和恢复检查脚本；
- 本地编排脚本，负责打包、上传、远程预检、部署、运行、下载证据和清理；
- 操作手册与真实结果报告模板；
- 配置结构、命令参数、夹具清理边界和结果判定的自动化测试。

本地编排脚本采用 fail-fast：后续步骤不能掩盖首个失败。清理在独立阶段执行，即使主测试
失败也要报告清理是否成功；若清理失败，必须输出精确的 `runId` 和人工恢复命令，但不得
自动扩大删除范围。

## 8. 完成标准

阶段 4D 只有在下列条件全部满足时才能标记完成：

1. 本地后端、前端及新增脚本静态检查通过；
2. 虚拟机双后端、Nginx、现有 MySQL 和现有 Redis 的真实链路启动成功；
3. 双实例分流和共享 Redis 限流证据成立；
4. Redis 正常与故障两组 100 人竞争 20 名额均通过数据库终态检查；
5. Redis 恢复检查通过；
6. 测试数据精确清理，既有业务数据指纹保持一致；
7. 真实报告和必要证据已生成，结论没有超出测试环境；
8. 阶段 4D 专用容器与远程临时目录已回收；
9. 一次性远程公钥和本地临时私钥已删除。

如果运行环境或任一硬性正确性门槛未通过，只能报告部分完成和具体阻塞，不能用源码测试、
历史结果或准备好的脚本替代真实验收。
