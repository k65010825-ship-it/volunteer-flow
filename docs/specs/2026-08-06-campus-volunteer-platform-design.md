# 校园志愿活动报名与候补平台设计规格

日期：2026-08-06  
状态：设计已确认，等待最终审阅  
暂定名称：VolunteerFlow

## 1. 项目定位

本项目面向班级、学生社团和校园志愿组织，解决以下真实问题：

- 活动信息散落在 QQ 群消息中，成员容易错过报名和变更通知。
- 报名人数达到上限后，没有公开、可验证的候补顺序。
- 已报名成员临时冲突时，往往只能私聊负责人取消，空出的名额难以及时递补。
- 活动负责人需要在表格、群聊和私聊之间反复核对名单。
- 活动现场缺少统一的签到和事后统计手段。

产品定位为“面向班级与社团的校园志愿活动报名、候补、签到与通知平台”。第一版采用适合手机访问的 Web 应用，通过 QQ 分享链接传播。用户本人担任首位组织负责人，并邀请至少 10 名同学参与真实或模拟试用。

## 2. 目标与非目标

### 2.1 第一版目标

- 支持平台管理员创建组织并指定组织负责人。
- 支持用户通过邀请链接或邀请码加入组织。
- 支持活动草稿、发布、取消和结束。
- 支持先到先得和人工审核两种报名模式。
- 支持公开规则下的候补、取消、递补和限时确认。
- 支持活动变更、报名结果和候补邀请的站内通知。
- 支持动态签到码、人工补签和签到统计。
- 支持多组织数据隔离、角色权限和关键操作审计。
- 支持 Docker Compose 部署，并提供自动化测试、压测和监控证据。

### 2.2 第一版非目标

- 不处理收费、退款或支付。
- 不建设面向全校的公开社交广场。
- 不提供通用聊天室；活动聊天室属于第二版。
- 不使用地理位置作为签到条件。
- 不自动处罚迟取消或未到场成员，只记录事实。
- 不建设任意可配置的审批工作流。
- 不拆分微服务。
- 不提供推荐算法或自动活动匹配。
- 不采集身份证等非必要的高敏感信息。

## 3. 总体架构

系统采用“模块化单体 + 事件驱动扩展”，避免在学习阶段承担微服务的部署和分布式事务成本。

```text
Vue 3 响应式 Web
        |
      Nginx
        |
Spring Boot 模块化单体
├─ auth
├─ organization
├─ activity
├─ registration
├─ checkin
├─ notification
├─ audit
└─ infrastructure
        |
├─ MySQL：最终事实来源
├─ Redis：缓存、限流、短期状态和并发优化
└─ Kafka：通知、统计等异步事件
```

架构原则：

- MySQL 决定最终业务结果。
- Redis 只做性能和体验增强，故障时核心报名流程能够回退数据库。
- Kafka 不进入报名主事务，故障时核心业务仍可成功。
- 模块之间优先通过明确的服务接口和领域事件协作，禁止跨模块随意访问内部表和实现类。
- 第二版聊天室与 AI 能力作为独立扩展设计，不污染第一版核心模型。

## 4. 角色与权限

### 4.1 角色

- 平台管理员：创建组织、指定组织负责人、处理平台级问题。
- 组织负责人：管理组织资料、成员角色和本组织全部活动。
- 活动管理员：管理本组织活动、报名审核、候补和签到。第一版暂不细分到单个活动。
- 普通成员：浏览活动，操作自己的报名、候补邀请、签到和通知。

### 4.2 加入与授权

平台管理员创建组织并指定负责人。负责人生成邀请链接或邀请码，成员使用邀请信息加入组织。负责人可将成员提升为活动管理员。

前端隐藏按钮只改善体验，所有权限必须由后端重新验证。资源查询必须同时限制当前用户、组织和资源归属；跨组织资源统一返回 404，避免泄露资源是否存在。

## 5. 核心业务规则

### 5.1 活动生命周期

活动状态：

- `DRAFT`：草稿，可编辑全部字段。
- `PUBLISHED`：已发布，成员可见。
- `FINISHED`：已结束，只读并进入统计阶段。
- `CANCELED`：已取消，不再允许报名或签到。

报名是否开放根据报名开始时间、截止时间和活动状态动态计算，不额外保存容易失真的“报名中”字段。

发布后，与报名结果有关的关键字段不能静默修改。时间、地点等变更必须走活动变更流程，保存变更前后内容并通知已报名成员。

### 5.2 报名模式

#### 先到先得 `FIRST_COME`

- 有可用名额时直接确认。
- 名额已满时进入候补队列。
- 候补顺序由本次候补生命周期内不可修改且不重复的 `queueNumber` 决定。
- 负责人不能手工拖拽或调整顺序。

#### 人工审核 `REVIEW`

- 报名后进入待审核状态。
- 负责人可以通过、加入候选池或拒绝。
- 正式成员取消后，由负责人从候选池选择递补人员。

### 5.3 报名状态

- `PENDING_REVIEW`：等待审核。
- `CONFIRMED`：已获得名额。
- `WAITLISTED`：在候补队列或候选池中。
- `REJECTED`：审核未通过。
- `CANCELED`：在免费取消期内取消。
- `LATE_CANCELED`：超过免费取消期后取消。

同一用户在同一活动只能有一条报名主记录。允许重新报名时复用该主记录并开启新的报名生命周期，同时在审计日志中保留上一次取消结果。每次重新进入候补队列都必须生成新的、更靠后的 `queueNumber`；该号码在本次候补生命周期内不可修改。

### 5.4 名额占用

名额占用数定义为：

```text
已确认报名人数 + 尚未结束的候补名额邀请数
```

候补邀请发出后，名额在确认期限内被保留，不能同时给其他人。邀请状态包括：

- `PENDING`
- `ACCEPTED`
- `DECLINED`
- `EXPIRED`
- `CANCELED`

确认期限由活动负责人配置，可选 30 分钟至 12 小时，默认 2 小时。接受后转为正式成员；拒绝或过期后退出当前队列，并把名额提供给下一位。用户需要重新报名时回到队尾。

邀请的 `expiresAt` 保存在 MySQL。Redis 倒计时只用于体验增强，定时任务根据数据库时间处理过期，并通过锁和状态条件保证幂等。

### 5.5 取消与未到场

- 活动配置免费取消截止时间。
- 截止前取消记录为 `CANCELED`。
- 截止后取消必须填写原因，记录为 `LATE_CANCELED`。
- 已确认但既未取消又未签到者，在活动结束后记录为未到场。
- 第一版不自动扣信用分或封禁，但保留后续统计所需的数据。

### 5.6 自定义报名表

用户姓名、学号和联系方式从个人资料自动填充。每个活动最多添加 5 个自定义问题，支持：

- `TEXT`
- `SINGLE_CHOICE`
- `MULTIPLE_CHOICE`
- `BOOLEAN`

问题可设置必填。活动发布后问题不可修改，避免历史答案失去语义。联系方式仅本人和有权限的管理员可见。

### 5.7 签到

- 负责人开启签到场次后生成短期、周期性更新的签到码。
- Redis 保存签到码和 TTL，MySQL 保存签到场次与最终签到结果。
- 签到请求必须同时验证已登录用户、活动资格和动态码；知道动态码本身不能冒充其他用户签到。
- 每个用户每场活动最多一条签到记录。
- Redis 故障时允许负责人人工补签，必须填写原因并写审计日志。
- 第一版不使用定位，避免权限、隐私和误差问题。

## 6. 关键流程

### 6.1 成员流程

```text
QQ 邀请链接
→ 登录或注册
→ 加入组织
→ 浏览活动
→ 查看规则并报名
→ 已确认 / 待审核 / 候补
→ 接受候补邀请（如有）
→ 查看活动变更
→ 现场签到
```

### 6.2 先到先得递补

```text
正式成员取消
→ 同一事务更新报名、审计和 Outbox
→ 事件发布到 Kafka
→ 递补任务选择 queueNumber 最小的有效候补
→ 创建限时 promotion_offer 并保留名额
→ 用户接受：转为 CONFIRMED
→ 用户拒绝或超时：释放名额并处理下一位
```

Kafka 或消费者故障时，由周期性补偿任务扫描“有空位但没有有效邀请”的活动，保证递补最终继续执行。

### 6.3 审核模式递补

正式成员取消后，系统提醒负责人存在空余名额。负责人从候选池选择用户并发出限时邀请，所有选择行为写入审计日志。

## 7. 数据模型

### 7.1 核心表

- `user`：账号、基础资料、密码摘要和状态。
- `organization`：组织资料和状态。
- `organization_member`：成员关系和组织角色，唯一键为 `(organization_id, user_id)`。
- `organization_invite`：邀请信息、失效时间和使用限制。
- `refresh_session`：刷新令牌摘要、轮换关系、失效时间和撤销状态。
- `activity`：活动信息、模式、时间、容量、状态和乐观锁版本。
- `activity_change`：已发布活动的重要变更、变更前后内容和通知状态。
- `activity_question`：发布时固化的报名问题。
- `registration`：报名主记录、状态、队列号、取消信息和到场结果，唯一键为 `(activity_id, user_id)`。
- `registration_answer`：报名答案。
- `promotion_offer`：候补邀请、状态和过期时间。
- `checkin_session`：签到场次。
- `checkin_record`：签到结果，唯一键为 `(activity_id, user_id)`。
- `notification`：站内通知、已读状态和关联业务。
- `audit_log`：只追加的关键操作记录。
- `outbox_event`：待发布的领域事件。

### 7.2 数据边界

- 所有组织业务表显式携带 `organization_id`。
- 用户敏感字段默认不进入公共 DTO。
- `queueNumber` 在一次候补生命周期内不能修改；重新报名时分配新号码。页面上的当前候补位次通过有效候补计算。
- `registration.attendance_status` 使用 `NOT_REQUIRED`、`PENDING`、`CHECKED_IN`、`NO_SHOW`；活动结束后把仍为 `PENDING` 且没有签到记录的已确认成员更新为 `NO_SHOW`。
- 审计记录只追加，不允许普通业务逻辑修改或删除。
- 业务记录、关键审计和 Outbox 在同一个数据库事务中写入。
- 第一版不创建聊天室和 AI 对话表。

## 8. 并发与一致性

### 8.1 报名事务

报名时先按活动维度尝试获取带所有者标识的 Redis 短期锁，再进入数据库事务：

1. 使用 `SELECT ... FOR UPDATE` 锁定活动或容量控制记录。
2. 校验活动状态、报名时间和用户现有报名。
3. 计算已确认人数与有效邀请数。
4. 创建确认记录或候补记录。
5. 写入审计和 Outbox。
6. 提交事务后释放 Redis 锁；只能由锁所有者释放。

Redis 锁不是最终正确性保证。数据库行锁、事务、状态条件和唯一约束共同防止超卖与重复报名。

重复请求返回当前报名状态或明确冲突，不创建第二条有效记录。接口后续可增加显式幂等键，但第一版至少通过业务唯一约束保证安全重试。

### 8.2 Redis 使用范围

- Cache Aside 活动详情缓存。
- 登录、报名和签到限流。
- 动态签到码和 TTL。
- 短期候补倒计时展示。
- 报名并发优化锁。

Redis 不可用时：缓存回源 MySQL，报名退化为数据库锁，动态扫码暂时不可用并使用人工补签。

### 8.3 Kafka 与 Outbox

主题建议：

- `activity-events`
- `registration-events`
- `checkin-events`

业务事务只写 `outbox_event`。独立发布器重试发送 Kafka，成功后标记事件已发布。消费者必须假设消息可能重复，并用事件编号和业务唯一键保证幂等。例如通知唯一键可为 `(event_id, user_id, channel)`。

关键审计同步写数据库；不能依赖 Kafka 异步记录。

## 9. API 设计

### 9.1 约定

- 基础路径：`/api/v1`。
- JSON 使用小驼峰命名。
- 使用 HTTP 状态码表达结果，不把所有请求包装为 200。
- 创建返回 201，成功且无响应体返回 204。
- 列表默认分页，单页上限 100。
- 管理表格采用页码分页；通知和审计采用游标分页。
- 使用 OpenAPI 3.1 描述接口并提供 Swagger UI。

成功响应可以使用 `data`，分页响应增加 `meta`。错误采用 RFC 7807 风格，包含稳定的 `code` 和用于日志关联的 `requestId`。

### 9.2 核心端点

```text
POST   /api/v1/auth/sessions
POST   /api/v1/auth/token-refreshes
DELETE /api/v1/auth/sessions/current
GET    /api/v1/users/me

POST   /api/v1/organizations/{orgId}/invitations
POST   /api/v1/organization-memberships

POST   /api/v1/organizations/{orgId}/activities
GET    /api/v1/organizations/{orgId}/activities
GET    /api/v1/activities/{activityId}
PATCH  /api/v1/activities/{activityId}
POST   /api/v1/activities/{activityId}/publication
POST   /api/v1/activities/{activityId}/cancellation

POST   /api/v1/activities/{activityId}/registrations
GET    /api/v1/activities/{activityId}/registrations
GET    /api/v1/registrations/{registrationId}
POST   /api/v1/registrations/{registrationId}/cancellation
POST   /api/v1/registrations/{registrationId}/review-decisions
POST   /api/v1/promotion-offers/{offerId}/responses

POST   /api/v1/activities/{activityId}/check-in-sessions
POST   /api/v1/check-in-sessions/{sessionId}/check-ins
POST   /api/v1/check-in-sessions/{sessionId}/manual-check-ins

GET    /api/v1/users/me/notifications
GET    /api/v1/organizations/{orgId}/audit-logs
```

### 9.3 错误分类

- 400：格式、类型或基础参数校验失败。
- 401：未登录、访问令牌失效或被篡改。
- 403：已登录但角色不允许操作。
- 404：资源不存在或不属于可见组织。
- 409：重复报名、状态冲突、邀请过期、并发修改。
- 422：请求语义本身不成立且与当前并发状态无关。
- 429：操作过于频繁。
- 503：暂时无法提供非核心依赖能力。

生产环境错误不得返回 SQL、堆栈和服务器目录。

## 10. 认证与安全

### 10.1 登录方案

- Access Token 使用短期 JWT，有效期建议 30 分钟，通过 Bearer Header 携带。
- Refresh Token 使用高强度随机值，服务端只保存摘要，放入 `HttpOnly`、`Secure`、`SameSite` Cookie。
- 刷新令牌每次使用后轮换；退出时撤销。
- 第一版同站点部署，避免不必要的跨站 Cookie 复杂度。
- 密码使用 BCrypt 哈希。
- 登录失败统一提示“用户名或密码错误”。

### 10.2 安全控制

- Bean Validation 限制人数、日期、文本长度和问题数量。
- MyBatis 使用参数绑定，禁止把用户输入放进 `${}`。
- 动态排序字段由后端白名单映射。
- 活动介绍第一版只接受纯文本。
- 邀请码、刷新令牌和签到码使用安全随机值。
- CORS 只允许部署前端域名，生产环境使用 HTTPS。
- 登录、报名、候补确认和签到分别限流。
- 日志脱敏密码、令牌和完整联系方式。
- 密钥通过环境变量或 Docker Secret 注入，禁止提交 Git。
- 发布、取消、审核、补签和角色变更写入审计。

## 11. 前端设计

### 11.1 技术与布局

使用 Vue 3、Vue Router、Pinia、Axios 和 Element Plus。一个项目通过响应式布局同时提供：

- 手机优先的成员端。
- 电脑优先的负责人管理端。

暂不引入第二套 UI 框架。第一版实时数据使用短轮询；聊天室阶段再统一引入 WebSocket。

### 11.2 页面

成员端：

- 登录、注册、邀请码加入。
- 活动广场和活动详情。
- 活动报名。
- 我的活动及状态筛选。
- 候补邀请与倒计时。
- 扫码签到。
- 通知中心和个人资料。

管理端：

- 数据概览。
- 活动创建、编辑、发布和取消。
- 报名审核、候补和名单管理。
- 现场签到和人工补签。
- 成员、角色、组织设置和审计日志。

### 11.3 关键交互

- 活动详情直接展示容量、确认人数、候补人数、报名规则、取消期限和自己的状态。
- 候补成员只看到自己的当前位次，不看到其他成员身份。
- 候补倒计时根据服务端 `expiresAt` 计算，刷新页面仍准确。
- 活动变更通知同时展示变更前和变更后内容。
- 创建活动采用分步表单和发布前检查清单。
- 发布后的关键字段必须通过变更流程处理。
- 人工补签必须填写原因。
- 每个核心页面设计加载、空数据、失败、无权限、网络断开、重复提交和状态冲突界面。

### 11.4 状态管理

Pinia 只保存当前用户、当前组织、登录状态和未读通知数。查询条件、弹窗和单页表单状态留在组件内。

Axios 负责附加 Access Token、单次刷新、统一错误转换和 `requestId`。刷新失败跳转登录。路由守卫只负责体验，不能替代后端权限。

## 12. 通知设计

第一版提供站内通知：

- 报名结果。
- 候补邀请。
- 活动变更。
- 签到提醒。
- 系统通知。

候补邀请和活动取消使用高优先级视觉样式。通知渠道通过接口抽象，未来可扩展邮件或其他机器人，但第一版不依赖 QQ 开放能力。

数据库通知是最终事实来源，前端未读角标仅为展示结果。Kafka 消费者重复消费不能生成重复通知。

## 13. 测试策略

### 13.1 测试分层

- JUnit 5、Mockito：报名、候补、取消、过期等领域规则。
- Spring Boot Test、MockMvc、Testcontainers：MySQL、Redis、Kafka 和事务。
- Vitest：前端状态转换和表单校验。
- Playwright：完整用户流程和移动端界面。
- k6：并发报名、活动查询和签到。
- 安全测试：认证、越权、注入、限流和敏感数据。

核心领域建议达到约 80% 分支覆盖率，不机械追求全项目 100%。测试使用工厂数据，禁止使用真实同学资料。

### 13.2 必测业务

- 最后一个名额正确确认，后续用户进入候补。
- 重复提交不生成重复有效报名。
- 截止后和活动取消后不能报名。
- 迟取消正确记录原因。
- 正式成员取消后触发递补。
- 邀请接受、拒绝和过期均正确推进状态。
- 过期邀请即使前端仍显示按钮也无法接受。
- 审核模式不会误走自动递补规则。

### 13.3 并发验收

使用 k6 让 100 个虚拟用户同时竞争 20 个名额：

- 确认人数不能超过 20。
- 每个用户最多一条有效报名。
- 其余用户进入候补且队列号不重复。
- 客户端重试不会制造重复记录。
- Redis 正常与故障回退时都不超卖。
- 普通查询 P95 目标低于 500ms；报名接口在该测试下 P95 目标低于 1s；非预期错误率低于 1%。

### 13.4 故障测试

- Redis 不可用时，查询回源数据库，报名退化到数据库锁。
- Kafka 不可用时，报名成功且 Outbox 保留。
- Kafka 恢复后事件补发，通知不重复。
- 消费者重复消费保持幂等。
- 服务在事务中异常时，业务、审计和 Outbox 同时提交或回滚。
- 动态签到不可用时人工补签可工作。

### 13.5 安全与端到端测试

建立两个组织和多个角色，验证跨组织越权、角色越权、他人报名操作、令牌篡改、登录限流、注入、错误泄露和隐私展示。

Playwright 至少覆盖：

1. 发布活动并完成报名。
2. 满员、取消、候补邀请和接受。
3. 人工审核报名。
4. 开启签到并完成扫码。
5. 无权限用户访问管理功能被拒绝。

## 14. 可观测性

使用 Spring Boot Actuator 和 Micrometer 暴露：

- API 请求量、错误率和 P95 延迟。
- 数据库连接使用情况。
- Redis 请求失败数。
- Kafka 消费积压。
- Outbox 未发布事件数。
- 报名成功、进入候补和递补次数。
- 候补接受、拒绝和过期比例。
- 签到、迟取消和未到场比例。

日志使用 `requestId` 串联 HTTP 请求、报名事务、Outbox、Kafka 和通知消费。增强阶段加入 Prometheus 与 Grafana；第一版先确保结构化日志和 Actuator 可用。

## 15. 部署

Docker Compose 包含：

- Nginx：Vue 静态资源和 `/api` 反向代理。
- Spring Boot。
- MySQL。
- Redis。
- Kafka KRaft 模式。
- 增强阶段的 Prometheus 和 Grafana。

数据库、Redis 和 Kafka 不直接暴露公网。MySQL 使用持久化 Volume，每日备份并至少完成一次恢复演练。健康检查区分进程存活与是否可接收请求。

## 16. 真实试用与产品验收

由开发者担任负责人，邀请至少 10 名同学完成一次真实或模拟活动：

1. 通过 QQ 分享活动链接。
2. 制造报名满员和候补状态。
3. 让一名已确认成员取消。
4. 验证候补邀请、限时接受和递补。
5. 完成现场扫码签到。
6. 收集参与者与负责人的反馈。

记录以下证据：

- 独立完成报名的人数和成功率。
- 用户是否理解当前报名状态和候补规则。
- 活动变更是否能被看见。
- 负责人是否仍需私聊处理名额。
- 最容易失败的操作步骤。
- 试用前后修改的功能及原因。

## 17. 分阶段交付

### 8 月核心版

1. 工程准备：模块结构、数据库迁移、统一错误和部署基础。
2. 组织与活动：登录、邀请、角色、活动发布与移动端查看。
3. 报名与候补：两种模式、取消、递补、限时确认和审计。
4. 通知与签到：站内通知、基础签到、人工补签和首次部署。

每天约 2 小时，优先完成业务闭环。若动态二维码来不及，可先使用短期签到码，但保留演进接口。

### 9 月工程增强

1. Redis：缓存、动态码、限流、并发锁和故障回退。
2. Kafka：事件、Outbox、幂等消费和补偿。
3. 测试与监控：Testcontainers、Playwright、k6、Prometheus、Grafana。
4. 真实试用：至少 10 名同学参与并形成反馈记录。

### 后续第二版

第一版稳定后，用独立规格开发活动聊天室：

- 每个活动绑定一个聊天室。
- 官方公告与普通讨论分离。
- 活动结束后只读归档。
- WebSocket 提供实时消息。
- Redis 管理在线状态，Kafka 承载消息事件和异步任务。

AI 能力按顺序加入：

1. 识别聊天中的活动变更候选，由负责人确认后才写入正式信息。
2. 生成未读消息摘要。
3. 基于活动资料和已确认公告进行 RAG 问答，并标注来源。

AI 不得自动更改活动、名单和报名状态；AI 不可用时聊天室仍必须工作。

## 19. 发布阻断条件

出现以下任何情况时不能上线试用：

- 报名人数可能超过活动容量。
- 同一用户可能获得重复有效报名或重复签到。
- 普通成员能够访问他人隐私数据。
- A 组织用户能够访问 B 组织管理资源。
- 候补邀请能够被重复接受或过期后接受。
- Kafka 或 Redis 故障会破坏报名最终数据。
- 生产日志输出密码、完整令牌或数据库堆栈。

## 20. 已知取舍与后续决策点

- 第一版活动管理员拥有本组织全部活动管理权限。若真实试用表明权限过大，再增加活动级管理员关联表。
- 第一版使用短轮询刷新签到和通知；聊天室阶段再引入 WebSocket。
- 第一版站内通知解决信息集中问题；外部通知渠道视开放能力和真实需求决定。
- 第一版只记录迟取消和未到场，不自动处罚；需要真实数据后再讨论信用规则。
- 当前使用一个响应式 Vue 项目；只有当成员端与管理端迭代节奏明显分离时才拆分前端应用。
- 项目暂定名称为 VolunteerFlow，正式名称可在创建仓库前调整。

## 21. 完成定义

项目第一阶段只有同时满足以下条件才算完成：

- 报名、候补、取消、递补、通知和签到形成完整闭环。
- 关键权限和跨组织隔离通过测试。
- 并发测试证明无超卖和无重复报名。
- Redis、Kafka 故障场景有明确验证结果。
- 可以通过 Docker Compose 部署演示。
- 至少 10 名同学完成一次试用并留下可分析反馈。
- 文档、测试报告和演示材料足以让面试官复现和理解项目。
