# VolunteerFlow 校园志愿活动报名与候补协同平台设计规格

- 日期：2026-09-14
- 状态：已完成讨论，等待文档复核
- 适用版本：第一版核心平台
- 技术基线：Java 17、Spring Boot 3.x、Vue 3、MySQL 8

## 1. 项目定位

VolunteerFlow 面向单所学校内的班级、学生社团和校园志愿组织，解决活动信息分散、报名状态不透明、临时退出依赖私聊协调、候补递补缺乏规则以及现场签到难以统计等问题。

第一版通过适合手机访问的 Web 页面供成员使用，并提供适合电脑操作的组织管理界面。活动链接可通过 QQ 等现有渠道分享，但核心报名、候补、通知和签到数据统一保存在平台中。

### 1.1 第一版目标

- 支持用户名和密码注册、登录及多设备会话。
- 支持平台管理员创建和停用组织。
- 支持邀请码加入组织。
- 支持组织级自定义 RBAC。
- 支持活动及多个志愿岗位的创建、发布、变更、取消和结束。
- 支持公共报名问题和岗位专属问题。
- 支持先到先得和人工审核两种岗位报名模式。
- 支持取消、候补、候选池、限时递补邀请和审计。
- 支持站内通知、签到、人工补签和到场统计。
- 支持 Docker Compose 部署、自动化测试、压测和监控证据。

### 1.2 非目标

- 不处理收费、退款或支付。
- 不建设面向全校的公开社交广场。
- 第一版不提供聊天室、推荐算法或 AI 功能。
- 不使用地理位置作为签到条件。
- 不自动处罚迟取消或未到场成员，只记录事实。
- 不拆分微服务。
- 不支持一个成员在同一组织拥有多个角色。
- 不支持一个成员同时报名同一活动的多个岗位。
- 不支持按多个用户属性自动匹配复杂配额。

## 2. 总体架构

系统采用前后端分离的模块化单体架构。前后端是两个独立工程，但保存在同一个 Git 仓库中。

```text
Vue 3 + TypeScript + Vite
            │ HTTP / JSON
Spring Boot 3.x + Java 17
├─ auth
├─ organization
├─ rbac
├─ activity
├─ registration
├─ checkin
├─ notification
├─ audit
└─ infrastructure
            │
   MyBatis-Plus + Flyway
            │
          MySQL 8
```

仓库结构：

```text
VolunteerFlow/
├─ backend/       # 使用 IDEA 开发
├─ frontend/      # 使用 VS Code 开发
├─ deploy/        # Docker Compose 与阶段 3 的 Nginx 配置
├─ docs/
├─ .env.example
├─ .gitignore
└─ README.md
```

### 2.1 后端模块职责

- `auth`：账号、认证、JWT 和刷新会话。
- `organization`：组织、成员和邀请码。
- `rbac`：权限、角色、角色授权和权限判定。
- `activity`：活动、岗位、报名问题和活动变更。
- `registration`：报名、审核、候补、候选池和递补邀请。
- `checkin`：签到场次、签到码和签到记录。
- `notification`：站内通知及未来通知渠道抽象。
- `audit`：只追加的关键操作审计。
- `infrastructure`：数据库、异常、日志、接口响应及外部组件适配。

模块通过明确的服务接口协作，不允许跨模块任意调用内部 Mapper。MyBatis-Plus 用于常规单表 CRUD、分页和条件查询；报名抢占、候补递补、容量统计和 `SELECT ... FOR UPDATE` 使用自定义 Mapper 和显式 SQL。Flyway 是唯一的数据库结构迁移方式。

### 2.2 中间件接入原则

- 阶段 0 至阶段 3 仅依赖 MySQL，核心业务必须形成完整闭环。
- 阶段 4 接入 Redis，用于缓存、限流、动态签到码和并发辅助。
- 阶段 5 接入 Kafka 与 Transactional Outbox，用于异步通知和事件扩展。
- Redis 锁不是最终正确性保证，Kafka 不进入报名主事务。
- 阶段 0 的 Docker Compose 只启动 MySQL，不提前加入未使用的中间件依赖。

## 3. 认证与账号

### 3.1 用户资料

平台面向单所学校，不建立 `school` 表。用户使用用户名登录，学号只作为个人资料。

```text
username        必填，平台唯一
password_hash   BCrypt 摘要
real_name       必填
student_number  必填，平台唯一
contact         必填的通用联系方式，不限制为手机或 QQ
status          ACTIVE / DISABLED
platform_role   PLATFORM_ADMIN / USER
```

联系方式仅本人和有权限的组织管理员可见。用户、组织、活动等核心记录通过状态停用或取消，不物理删除。

### 3.2 多设备会话

- Access Token 使用短期 JWT，建议有效期 30 分钟。
- Refresh Token 使用高强度随机值，通过 `HttpOnly` Cookie 保存。
- 服务端只保存 Refresh Token 摘要。
- 每台设备对应一条独立 `refresh_session`。
- 刷新令牌每次使用后轮换，旧令牌立即失效。
- 退出当前设备只撤销当前会话；账号停用时撤销全部会话。
- 迁移脚本不得写入固定管理员密码；初始管理员通过明确的部署初始化流程创建。

## 4. 组织与 RBAC

### 4.1 平台与组织边界

平台级身份固定为 `PLATFORM_ADMIN` 和 `USER`。平台管理员负责组织创建、停用及平台级问题，不依赖组织角色。

组织内部使用自定义 RBAC：

- 权限编码由平台预置，组织不能创建新权限编码。
- 每个组织可以创建、编辑、停用和删除符合条件的自定义角色。
- 每个组织成员只能拥有一个角色。
- 用户最终权限等于该成员当前角色拥有的权限集合。
- 第一版不提供拒绝权限、字段级权限或单个活动级授权。

创建组织时自动生成：

- 组织负责人：始终拥有当前及未来全部组织权限，不可删除或削减关键权限。
- 活动管理员：预置活动、报名、候补和签到管理权限，可由负责人调整。
- 普通成员：预置成员基本权限，可由负责人调整。

组织必须至少保留一名有效负责人。使用中的角色不能删除；角色停用前必须迁移其成员。角色变更、权限变更和成员角色分配均写入审计日志。

权限编码示例：

```text
organization:manage
member:invite
member:role_assign
role:create
role:update
activity:create
activity:publish
activity:change
activity:cancel
registration:review
registration:promote
checkin:manage
audit:read
```

负责人角色通过受保护的内置角色类型获得全部组织权限，避免未来新增权限后负责人意外失去管理能力。

### 4.2 邀请码

- 默认有效期 7 天，默认最多使用 50 次。
- 创建者可以设置有效期和最大使用次数，也可以主动停用。
- 达到使用次数、过期或停用后不可使用。
- 邀请码使用安全随机值，数据库仅保存摘要，完整值只在创建后展示一次。
- 邀请默认加入为普通成员；授权人员可在加入后调整角色。
- 创建成员关系和增加使用次数必须在同一事务中完成。
- 同一用户重复使用邀请码不创建第二条成员关系，也不重复占用次数。

## 5. 活动与岗位

### 5.1 活动生命周期

```text
DRAFT → PUBLISHED → FINISHED
                  ↘ CANCELED
```

报名未开始、报名中、报名截止和活动进行中根据活动状态及时间动态计算，不额外保存容易失真的状态字段。到达结束时间后由幂等定时任务自动标记为 `FINISHED`，管理员也可以提前手动结束。

### 5.2 志愿岗位

岗位是活动内部的一级业务实体。例如：

```text
新生开学典礼
├─ 礼仪岗：10 人，人工审核
├─ 疏导岗：20 人，先到先得
└─ 讲解岗：8 人，人工审核
```

每个岗位独立保存：

- 岗位名称和工作说明。
- 招募容量。
- 报名模式：`FIRST_COME` 或 `REVIEW`。
- 候补邀请确认时限。
- 可选的岗位服务时间和集合地点；为空时继承活动设置。
- 已确认人数、候补人数等通过业务数据计算，不保存冗余计数作为最终事实。

活动总容量由岗位容量之和计算。活动发布前至少包含一个有效岗位。

### 5.3 发布后变更

- 标题、介绍、地点和活动时间通过活动变更流程修改。
- 报名开始后不能修改报名开始时间。
- 报名截止时间可延后；提前时必须晚于当前时间，且不能破坏已产生的报名状态。
- 已有岗位不得删除或更改报名模式。
- 已有岗位容量只能增加，不能减少。
- 岗位名称、说明、服务时间和地点通过正式变更流程修改。
- 发布后允许新增岗位，并发布变更通知。
- 已发布活动的已有问题结构不可修改。
- 已取消或已结束的活动不得继续修改或新增岗位。
- 所有重要变更保存变更前后值，并通知受影响成员。

## 6. 报名表

报名表由两层问题组成：

- 活动公共问题：报名任一岗位时都要回答。
- 岗位专属问题：选择相应岗位后才出现。

姓名、学号和联系方式从个人资料带入，不计入自定义问题。每次报名最多展示 10 个自定义问题，公共问题和岗位问题合计不得超过 10 个。

问题类型：

```text
TEXT
SINGLE_CHOICE
MULTIPLE_CHOICE
BOOLEAN
```

问题可设置必填。活动发布后，公共问题以及已存在岗位的问题均被冻结；发布后新增岗位可以配置自身的岗位问题。

## 7. 报名、候补与递补

### 7.1 通用规则

- 同一成员在同一活动只能报名一个岗位。
- 数据库以 `(activity_id, user_id)` 保证报名主记录唯一。
- 换岗必须取消原报名后重新报名，新岗位不继承原岗位的顺序。
- 原岗位名额释放时按该岗位规则触发递补。
- 管理员不能静默移动成员到其他岗位。
- 重新报名生成新的报名周期，并保留此前周期、答案及状态历史。

报名主记录 `registration` 表示成员与活动的稳定关系；`registration_cycle` 保存每次报名尝试的岗位、状态、候补序号和取消信息；`registration_answer` 关联具体报名周期。这避免覆盖重报前的答案和状态。

报名周期状态：

```text
PENDING_REVIEW
CONFIRMED
WAITLISTED
REJECTED
CANCELED
LATE_CANCELED
PROMOTION_DECLINED
PROMOTION_EXPIRED
```

### 7.2 先到先得岗位

```text
提交报名
├─ 有空位 → CONFIRMED
└─ 已满   → WAITLISTED
```

候补序号在本次报名周期内不可修改且不重复。成员可看到自己的候补序号、当前有效名次、候补总人数和递补规则，但不能看到其他候补者身份。取消或退出后重新报名会获得新的队尾序号。

正式成员取消或岗位增加容量后，系统按最小有效候补序号发出限时递补邀请。

### 7.3 人工审核岗位

```text
提交报名 → PENDING_REVIEW
              ├─ 录取   → CONFIRMED
              ├─ 候选池 → WAITLISTED
              └─ 拒绝   → REJECTED
```

候选池没有固定公开顺序，不展示候补名次。出现空位时，由有权限的管理员选择候选人并发送限时邀请。审核、选择和邀请记录操作者及理由。

### 7.4 递补邀请

- 确认时限配置在岗位层级，默认 2 小时，可配置为 30 分钟至 12 小时。
- 发出邀请后立即预留该岗位名额。
- 岗位占用数等于 `CONFIRMED` 数量加尚未结束的有效邀请数量。
- 接受后转为 `CONFIRMED`。
- 拒绝或超时后退出本次报名周期；如需再次参加，必须重新报名。
- 先到先得岗位在拒绝或超时后自动邀请下一名候补。
- 人工审核岗位在拒绝或超时后只通知管理员，不自动选择下一人。

邀请状态：

```text
PENDING
ACCEPTED
DECLINED
EXPIRED
CANCELED
```

`expires_at` 保存在 MySQL。定时任务根据数据库时间处理过期，并以状态条件更新保证幂等。

### 7.5 取消与未到场

- 活动配置免费取消截止时间。
- 截止前取消记为 `CANCELED`。
- 截止后取消必须填写原因，记为 `LATE_CANCELED`。
- 活动结束后，已确认但未取消且没有签到记录的成员标记为未到场。
- 第一版只记录迟取消和未到场，不自动扣分、封禁或降低报名优先级。

## 8. 签到与通知

### 8.1 签到

- 管理员为活动开启和关闭签到场次。
- 阶段 3 先实现短期普通签到码。
- 签到必须同时验证登录用户、活动资格、签到场次和签到码。
- 每个用户在每个活动最多有一条有效签到记录。
- 管理员可以人工补签，但必须填写原因并记录审计。
- 阶段 4 使用 Redis TTL 实现周期更新的动态签到码。
- Redis 不可用时，动态扫码可暂停，但人工补签必须可用。

### 8.2 站内通知

第一版通知类型包括：

- 报名和审核结果。
- 候补邀请及过期提醒。
- 活动或岗位变更。
- 活动取消。
- 签到提醒。
- 系统通知。

数据库通知是最终事实来源。阶段 0 至阶段 3 在业务事务内同步写通知；阶段 5 通过 Outbox 与 Kafka 异步创建，同时使用唯一键防止重复通知。

## 9. 核心数据模型

```text
认证
app_user
refresh_session

组织与权限
organization
organization_invite
organization_member
rbac_role
rbac_permission
rbac_role_permission

活动
activity
activity_position
activity_change
activity_question
activity_position_question

报名
registration
registration_cycle
registration_answer
promotion_offer

签到与协作
checkin_session
checkin_record
notification
audit_log
outbox_event
```

关键约束：

- `app_user.username` 唯一。
- `app_user.student_number` 唯一。
- `organization_member (organization_id, user_id)` 唯一。
- `rbac_role (organization_id, name)` 唯一。
- `rbac_role_permission (role_id, permission_id)` 唯一。
- `registration (activity_id, user_id)` 唯一。
- `registration_cycle (registration_id, cycle_number)` 唯一。
- 每个先到先得岗位的候补序号在岗位范围内唯一。
- `checkin_record (activity_id, user_id)` 唯一。
- 通知消费者按事件编号、用户和渠道建立业务唯一约束。

所有组织业务表显式携带 `organization_id`。核心审计记录只追加，不允许普通业务逻辑修改或删除。业务数据、关键审计和 Outbox 在需要时同事务写入。

Flyway 按领域拆分迁移文件，并在阶段 0 建立第一版全部核心表；后续只能通过新迁移补充字段、约束或索引。

## 10. API 与错误处理

### 10.1 约定

- 基础路径为 `/api/v1`。
- 健康检查使用 `/actuator/health`，不纳入业务版本路径。
- JSON 使用小驼峰命名。
- 创建返回 `201`，成功且无响应体返回 `204`。
- 列表默认分页，单页上限 100。
- 成功响应使用 `data`，分页响应增加 `meta`。
- 错误响应采用 Problem Details 风格，并包含稳定的 `code` 和 `requestId`。

### 10.2 主要资源

```text
/auth/sessions
/auth/token-refreshes
/users/me
/organizations/{orgId}
/organizations/{orgId}/invitations
/organizations/{orgId}/members
/organizations/{orgId}/roles
/organizations/{orgId}/activities
/activities/{activityId}/positions
/activities/{activityId}/questions
/positions/{positionId}/questions
/positions/{positionId}/registrations
/registrations/{registrationId}
/promotion-offers/{offerId}
/check-in-sessions/{sessionId}
/users/me/notifications
/organizations/{orgId}/audit-logs
```

发布、取消、审核和邀请响应使用能表达业务含义的子资源端点，例如：

```text
POST /activities/{id}/publication
POST /activities/{id}/cancellation
POST /registrations/{id}/cancellation
POST /registrations/{id}/review-decisions
POST /promotion-offers/{id}/responses
```

### 10.3 错误分类

- `400`：格式、类型或基础参数校验失败。
- `401`：未登录、Access Token 失效或会话被撤销。
- `403`：身份有效，但没有操作权限。
- `404`：资源不存在或不属于当前可见组织。
- `409`：重复报名、状态冲突、邀请过期或并发修改。
- `422`：请求在当前业务规则下不成立。
- `429`：操作过于频繁。
- `503`：非核心依赖能力暂时不可用。

生产响应不得包含 SQL、堆栈、服务器路径、密码、令牌或完整敏感联系方式。

## 11. 并发与一致性

### 11.1 报名事务

1. 校验活动、岗位、报名时间和用户资格。
2. 使用 `SELECT ... FOR UPDATE` 锁定目标岗位记录。
3. 计算该岗位已确认人数与有效待确认邀请数。
4. 创建或更新报名周期为确认、待审核或候补状态。
5. 写入报名答案、审计和第一阶段所需通知。
6. 提交事务。

数据库行锁、事务、唯一约束和状态条件共同防止超卖与重复报名。客户端重复请求返回当前状态或明确冲突，不创建第二条有效记录。

### 11.2 Redis

阶段 4 使用 Redis 实现：

- Cache Aside 活动详情缓存。
- 登录、报名、邀请确认和签到限流。
- 动态签到码及 TTL。
- 候补倒计时展示辅助数据。
- 报名的短期分布式辅助锁。

Redis 不可用时，查询回源 MySQL，报名退化为数据库锁，核心数据仍正确；动态扫码暂时不可用并允许人工补签。

### 11.3 Kafka 与 Outbox

阶段 5 引入活动、报名和签到事件。业务事务只写 `outbox_event`，独立发布器重试发送 Kafka，成功后标记已发布。消费者假设消息可能重复，并以事件编号和业务唯一键实现幂等。

Kafka 故障不得导致报名失败。Kafka 恢复后补发事件，不能生成重复通知。数据库补偿任务扫描存在空位但没有有效邀请的岗位，保证递补最终继续执行。

## 12. 前端设计

前端为一个 Vue 3 + TypeScript + Vite 工程，通过响应式布局和权限路由提供手机优先的成员端与桌面优先的管理端。

### 12.1 成员端

- 注册、登录和邀请码加入。
- 活动列表、筛选、活动与岗位详情。
- 公共问题和岗位问题组成的报名表。
- 我的报名及状态筛选。
- 候补名次、邀请倒计时、接受和拒绝。
- 通知中心、个人资料和签到页面。

### 12.2 管理端

- 数据概览。
- 活动、岗位和报名问题管理。
- 发布、正式变更、取消和提前结束。
- 先到先得队列、人工审核和候选池。
- 签到与人工补签。
- 组织成员、角色、权限、邀请码和审计日志。

### 12.3 状态管理

- Pinia 只保存当前用户、当前组织、登录状态、有效权限编码和未读通知数。
- 活动、岗位和报名列表按页面请求，不长期复制到全局 Store。
- 路由守卫只改善体验，不能替代后端权限校验。
- Axios 统一附加令牌、执行单次刷新、转换错误并展示 `requestId`。
- 关键提交按钮在请求期间禁用，防止重复操作。
- 倒计时根据服务端 `expiresAt` 计算，刷新页面后仍以服务端结果为准。
- 每个核心页面处理加载中、空数据、失败、无权限、断网和状态冲突。

开发阶段由 Vite 将 `/api` 和 `/actuator` 代理至 Spring Boot。阶段 3 构建静态资源并由 Nginx 托管，同时反向代理后端接口。

## 13. 测试与验收

### 13.1 测试分层

- JUnit 5：活动、岗位、报名、取消、候补和邀请规则。
- Spring Boot Test + Testcontainers：MySQL、Flyway、事务、行锁及权限隔离。
- Vitest：报名表、权限展示、状态转换和倒计时。
- Playwright：发布、报名、审核、候补、邀请确认、签到和越权流程。
- k6：100 名虚拟用户竞争多个岗位的有限名额。

### 13.2 必测场景

- 每个岗位的确认人数不超过岗位容量。
- 同一成员不能占用同一活动的多个岗位。
- 第一个超出容量的成员正确进入该岗位候补队列。
- 正式成员取消后，正确邀请该岗位第一名有效候补。
- 邀请预留期间名额不会分配给其他成员。
- 邀请接受、拒绝和过期均只能成功处理一次。
- 人工审核候选池不会误用自动队列规则。
- 发布后岗位增容能触发正确递补。
- Redis 正常或故障时均不超卖。
- Kafka 停机期间业务成功，恢复后通知补发且不重复。
- 跨组织资源、他人报名和无权限管理接口均不能访问。

### 13.3 并发验收

使用 k6 模拟 100 名用户并发报名多个岗位：

- 任一岗位的确认人数不得超过容量。
- 每名用户最多只有一个有效活动报名。
- 候补序号不重复。
- 客户端重试不生成重复记录。
- Redis 正常和故障回退时结果均正确。
- 延迟和错误率只记录真实测试结果，不预先编造。

## 14. 日志、监控与发布阻断

使用结构化日志和 `requestId` 关联 HTTP 请求、业务事务、Outbox、Kafka 和通知消费。阶段 6 使用 Actuator、Micrometer、Prometheus 和 Grafana 监控：

- API 请求量、错误率和延迟。
- 数据库连接池使用情况。
- Redis 请求失败数。
- Kafka 消费积压。
- Outbox 未发布事件数。
- 报名成功、进入候补和递补次数。
- 邀请接受、拒绝和过期比例。
- 签到、迟取消和未到场比例。

出现以下任一情况时禁止提供真实试用：

- 任一岗位可能超卖。
- 同一成员可能重复报名或重复签到。
- 邀请可以重复接受或过期后接受。
- 普通成员可以查看他人敏感资料。
- 一个组织的用户可以访问另一个组织的管理资源。
- Redis 或 Kafka 故障会破坏报名最终数据。
- 生产日志包含密码、完整令牌、数据库堆栈或完整联系方式。

## 17. 第二版：聊天室与 AI

第一版稳定后单独编写第二版需求文档。聊天室为每个活动提供一个房间，区分官方公告和普通讨论，活动结束后只读归档。WebSocket 提供实时消息，Redis 管理在线状态，Kafka 承载消息事件和异步任务。

AI 按以下顺序接入：

1. 从聊天内容识别可能的活动变更，必须由负责人确认后才写入正式信息。
2. 生成未读消息摘要。
3. 基于活动资料和已确认公告进行带来源的问答。

AI 不得直接修改活动、岗位、名单、报名或签到状态；模型不可用时聊天室仍须正常工作。
