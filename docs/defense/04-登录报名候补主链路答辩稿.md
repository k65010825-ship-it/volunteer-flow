# VolunteerFlow 登录、报名与候补递补主链路答辩稿

> 登录 -> 报名 -> 候补

---

## 一、开场：项目解决什么问题

### 讲述稿

VolunteerFlow，是一个面向班级、社团和校园志愿组织的活动报名与候补协同平台。

我观察到传统志愿活动通常通过群聊、在线表格或者临时问卷组织。这种方式有个明显问题：第一，一个活动可能同时招募礼仪、疏导、讲解等不同岗位，各岗位的名额、问题和要求并不相同；第二，活动满员后候补顺序不透明，正式成员取消时往往需要负责人手工联系。

```text
用户登录
→ 选择活动和岗位
→ 填写动态报名表
→ 提交报名
→ 有名额则正式录取
→ 满员则进入候补
→ 正式成员取消
→ 第一名候补获得限时邀请
→ 接受邀请后转为正式成员
```

这条链路的核心目标是：不超卖、不重复报名、候补顺序稳定、邀请不会被重复接受，并且关键操作可审计。

## 三、登录链路：短期 JWT 与可撤销刷新会话

### 讲述稿

后端首先根据用户名查询用户，然后检查账号是否为 `ACTIVE`，（**登录时**）禁止被停用的账号获得令牌。

为了系统的安全性，我是采用了 BCrypt 算法校验密码摘要，数据库不会保存明文密码。

登录成功后，后端同时签发两种令牌：

1. 有效期较短的 JWT Access Token，默认30分钟。
2. 有效期较长的随机 Refresh Token，默认30天。

Access Token 用来访问业务接口；

Refresh Token 只访问刷新接口，用来维护登录状态。

具体来说就是 Access Token 过期后，客户端使用 Refresh Token 请求新的 Access Token；然后服务端同时轮换 Refresh Token，防止 Refresh Token 泄露时，攻击者能持续换取新 JWT。

这种双令牌的设计既可以缩短 JWT Access Token 泄露后的可用时间又可以确保用户登录体验。

**边界：**但如果某个 JWT Access Token 已被窃取，它理论上仍可能使用到剩余的 30 分钟结束。所以我这边其实还可以加入一个 Redis 黑名单来拒绝。

项目中，我把 Access Token 保存在前端内存中，Axios 请求拦截器将它放到 `Authorization` 请求头。Refresh Token 放在 `HttpOnly`、`SameSite=Lax` 的 Cookie 中，前端 JavaScript 不能直接读取它，可以降低 XSS 窃取长期凭证的风险。

Refresh Token 也不会以明文写进数据库，后端只保存 SHA-256 摘要。刷新时通过摘要查询会话，并使用 `FOR UPDATE` 行锁查询旧令牌是否有效。

好处：保证旧令牌只能使用一次，防止两个并发刷新请求都使用旧令牌换到新令牌。因为，如果其中一个请求来自窃取令牌的人，他就能沿自己的令牌继续刷新，轮换失去了阻止重放的作用。并且先收到“刷新成功”响应的客户端，拿到的令牌可能马上失效，下一次刷新时被迫重新登录。

前端收到 401 时，Axios 响应拦截器会发起刷新。当页面中多个请求同时过期时共享同一个 `refreshPromise`，避免产生刷新风暴。刷新成功后重放原请求；刷新失败则清理登录状态并触发会话过期事件。

### 为什么不把 Access Token 放 localStorage

因为localStorage 中的数据可以被同源 JavaScript 读取，一旦发生 XSS，长期令牌更容易泄露。

### `DatabaseJwtAuthenticationConverter` 的作用

构造认证对象，并保存到 SecurityContext 上下文。

``` java
if (user == null || !"ACTIVE".equals(user.getStatus())) {
      throw invalidToken("User is unavailable");
    }
// 确保登录后被标记被失效账号立即失去访问能力
```

## 五、进入组织：平台身份与组织 RBAC

前面的认证解决的是身份问题。

RBAC 解决的时权限问题。

我这边设计了两级身份：一个是平台级的 `PLATFORM_ADMIN` 和 `USER`，还有一个就是组织级的 `OWNER`、`ACTIVITY_ADMIN`、`MEMBER` 和自定义角色。

- 平台管理员负责创建和停用组织，不会获得每个组织的内部业务权限；

- 组织负责人拥有组织内全部权限；

- 活动管理员负责活动发布、审核、递补等等；

- 普通成员负责查看活动、报名、取消和签到。

根据活动报名的常识，一个用户可以加入多个组织，但用户在同一个组织中只能拥有一个角色。所以我在`organization_member` 表中通过 `organization_id + user_id` 的唯一约束保证正确性。

敏感操作调用 requirePermission。

先检查有效成员关系，再检查角色是否属于当前组织、是否有效，最后查询角色权限。

如果是受保护的 `OWNER`，也就是组织负责人，则直接拥有全部组织权限。

当成员不属于这个组织时，访问资源返回 404，而不是直接暴露“组织存在但你没有权限”；

当成员属于组织，但权限不足时返回 403。

### 关键源码

- 组织授权：`OrganizationAuthorizationService.java`
- 默认角色和权限：活动管理员和普通成员---`OrganizationService.java`
- RBAC 表：`resources/db/migration/V4__create_rbac_tables.sql`

## 六、报名主事务：项目最核心的代码

### 讲述稿

报名入口是 `RegistrationSubmissionService.submit`，事务隔离级别显式使用 `READ_COMMITTED`。

没有用默认的可重复读是因为读已提交模式中

1. 普通 select 不会长期固定旧快照，正式决策通过 `select FOR UPDATE` 重新读取；
2. 相比RR，更容易控制锁范围，减少不必要的间隙锁和并发阻塞。

完整处理顺序是：

```text
校验请求
→ 读取报名表并确定组织
→ 锁定当前用户的组织成员记录
→ 锁定目标岗位并重新校验活动，校验原因：防止在用户打开页面到点击提交之间，活动取消
							     前端页面中的数据只能用于展示，不能作为服务端最终判断依据。
→ 检查报名时间窗口
→ 检查同一活动是否已有有效报名
→ 校验动态问题答案
→ 创建或复用 registration 主记录
→ 创建新的 registration_cycle
→ 根据岗位模式和容量决定初始状态
→ 保存答案快照
→ 写入审计记录
→ 事务提交
```

这里最重要的是固定的锁顺序：

```text
成员锁 → 岗位锁 → 报名周期锁 → 递补邀请锁
```

所有报名、取消和递补流程遵守统一顺序，可以降低死锁概率。

### 第一道锁：成员锁

系统先执行 `selectActiveMemberForUpdate` 锁定用户在组织中的成员记录。

它解决的是同一个用户同时报名同一个活动的不同岗位问题。假设用户双击或者在两个浏览器标签中同时报名礼仪岗和讲解岗，如果只锁岗位，就会出现问题。先锁成员记录后，同一个用户的并发报名会串行执行。

### 第二道锁：岗位锁

随后使用 `SELECT ... FOR UPDATE` 锁定岗位。

同一个岗位上的容量判断、候补序号分配、取消释放名额和递补邀请都围绕同一行串行执行。

如果 100 个用户同时争抢 20 个名额，获得岗位锁的请求会依次重新统计容量，因此最多只有 20 个请求进入 `CONFIRMED`。

### 为什么要重新读取活动和岗位

防止在用户打开页面到点击提交之间，活动被取消、报名窗口结束、岗位失效。

前端页面中的数据只能用于展示，不能作为服务端最终判断依据。

### 动态答案校验

客户端只提交 `questionScope`、`questionId` 和答案，不提交可信的题型或选项。服务端要根据数据库里问题的定义检查，比如：

- 必填题是否有答案；
- 单选答案是否属于合法选项；
- 多选值是否全部有效；
- 是否提交了不属于该岗位的问题；
- 是否重复回答同一道题。

答案以 JSON 快照保存在 `registration_answer`。

### 报名数据为什么拆成主记录和周期

系统没有把一次报名简单设计成一行，而是拆成：

```text
registration
└─ registration_cycle
   ├─ registration_answer
   └─ promotion_offer
```

`registration` 表示“某个用户与某个活动之间稳定的报名关系”，通过 `(activity_id, user_id)` 唯一约束保证同一用户在同一活动只有一条主记录。

`registration_cycle` 表示一次具体的报名尝试。用户取消后可以重新报名，让 `cycle_number + 1`就行，创建新周期。这样可以保留历史报名记录。

`registration_answer` 属于具体周期，因为用户重新报名时答案可能不同。

`promotion_offer` 也属于具体周期，并通过 `registration_cycle_id` 唯一约束保证一个报名周期最多创建一次递补邀请。

### 为什么不直接更新一行报名记录

会覆盖历史记录，无法说明“用户报名了几次、什么时候取消、当时填写了什么、哪次获得了邀请”。拆分能保证当前唯一性，也能保留完整生命周期。

## 七、活动和岗位

活动包含多个独立岗位。例如新生开学典礼可以同时招募礼仪、疏导和讲解人员。

每个岗位分别保存：

- 岗位名称和说明；
- 容量；
- 报名模式；
- 服务时间和集合地点；
- 递补确认时限；
- 下一个候补序号。

支持两种报名策略：

- `FIRST_COME`：先到先得，有名额直接 `CONFIRMED`，满员进入候补队列；
- `REVIEW`：提交后进入 `PENDING_REVIEW`，由组织/活动负责人选择确认、候补或拒绝。

报名问题也分为两层：活动公共问题和岗位专属问题。比如报名礼仪岗时，前端加载公共问题与礼仪岗问题的组合，而不会加载其他岗位的问题。

活动发布后不可以修改报名表。如果用户按旧问题提交时，负责人同时修改问题，会出现“用户回答的题目和后台当前题目不一致”的语义冲突。

### 为什么把容量放到岗位而不是活动

岗位之间不可互相替代。礼仪岗空缺并不代表讲解岗可以多录取一人。如果只保存活动总容量，就无法保证岗位人员结构正确，也无法定义清晰的候补队列。

### 关键源码

- 活动和岗位：`backend/src/main/java/com/volunteerflow/activity/ActivityService.java`
- 活动模块提供给报名模块的统一规则：`backend/src/main/java/com/volunteerflow/activity/ActivityRegistrationPolicyService.java`

## 八、先到先得：有名额确认，满员候补

状态机：

```tex
提交报名
├─ 有名额 → CONFIRMED
└─ 已满员 → WAITLISTED
               ├─ 获得邀请并接受 → CONFIRMED
               ├─ 拒绝 → PROMOTION_DECLINED
               ├─ 超时 → PROMOTION_EXPIRED
               └─ 主动取消 → CANCELED/LATE_CANCELED
```

对 `FIRST_COME` 岗位，系统在已经持有岗位锁的事务中计算占用数：

```text
占用数 = CONFIRMED 人数 + 尚未过期的 PENDING 递补邀请数
```

如果占用数小于岗位容量，新报名状态为 `CONFIRMED`；否则状态为 `WAITLISTED`。

这里必须把有效的 `PENDING` 邀请也算作占用。

因为邀请有效期内名额已经承诺给候补者。如果不占名额，系统可能又确认新的报名者，原候补接受时就会超卖。

进入候补时，从岗位的 `next_waitlist_sequence` 分配不可变序号，然后将该值加一。因为岗位行已经被锁定，所以并发请求不会获得相同序号。并且数据库也设置了 `(position_id, waitlist_sequence)` 。

页面显示两个概念：

- 原始候补序号：报名时获得，不会修改；
- 当前位次：实时统计前面仍处于 `WAITLISTED` 的人数再加一。

这样前面的人退出后，后面的当前位次自然前移，但历史排序证据仍保留。

## 九、人工审核模式

状态机：

```tex
提交报名 → PENDING_REVIEW
              ├─ CONFIRM → CONFIRMED
              ├─ WAITLIST → WAITLISTED（无序候选池）
              │               └─ 管理员发邀请 → 接受/拒绝/过期
              └─ REJECT → REJECTED
```

报名后进入 `PENDING_REVIEW`。

具有 `registration:review` 权限的 owner 或 manager 可以选择：

- `CONFIRM`：确认录取，但仍需在岗位锁下检查容量；
- `WAITLIST`：进入无序候选池；
- `REJECT`：拒绝报名。

人工审核岗位的候选池不分配 `waitlist_sequence`。出现空位后，由拥有 `registration:promote` 审核权限的管理者选择合适候选人并创建限时邀请。

两种模式复用了相同状态机和递补邀请模型，但候选人的选择策略不同：先到先得自动选择最小候补序号，人工审核由管理员选择。

### 关键源码

- 审核服务：`backend/src/main/java/com/volunteerflow/registration/RegistrationReviewService.java`

## 十、取消报名与自动递补

正式成员取消报名时，`RegistrationCancellationService` 按相同锁顺序执行。

```java
if (offer != null && "PENDING".equals(offer.getStatus())) {
      // 如果不设置released = true，
      // 直接把替补状态改为canceled的话
      // 那么这个替补邀请就既不生效，过期后又不会被定时任务扫描 
      // 因为定时任务只扫描邀请状态为pending的过期记录，
      // 那么就会阻塞候补队列
     //  应该将released设置为true，调用方法立刻执行替补逻辑		 
     //  (L122)
     // 为什么不把定时任务的扫描范围扩大到cancel和pending呢？
     // CANCELED 已经是终态，扫描后状态还是 CANCELED
     // 无法判断他是否已经推进过队列 -> 无法保证幂等
      released = true;
      offer.setStatus("CANCELED");
      offer.setRespondedAt(now);
```

报名截止时间之前取消，状态为 `CANCELED`；

报名截止时间之后取消，状态为 `LATE_CANCELED`，需要填写原因。

是否迟取消由数据库时间判断。

如果取消成功后，系统在同一个事务中调用 `offerNextFirstCome`：

1. 再次确认岗位有容量；
2. 查询没有获得过邀请的候补周期；
3. 锁定候补周期；
4. 创建状态为 `PENDING` 的递补邀请；
5. 设置 `expires_at`；
6. 写入审计日志。

这里没有直接把候补者改成 `CONFIRMED`，因为用户可能已经有其他安排。限时邀请给用户选择权，同时在有效期内保留这个名额。

### 为什么取消和递补必须在同一个事务

如果先提交取消，再创建邀请，可能会造成岗位有空位但没有人被递补。

### 关键源码

- 取消服务：`backend/src/main/java/com/volunteerflow/registration/RegistrationCancellationService.java`
- 递补服务：`backend/src/main/java/com/volunteerflow/registration/PromotionService.java`

## 十一、接受、拒绝和过期

### 接受邀请

用户点击接受时，重新执行以下校验：

- 邀请属于当前用户；
- 组织、活动、岗位和周期相互匹配；
- 邀请仍为 `PENDING`；
- 数据库当前时间早于 `expires_at`；
- 报名周期仍为 `WAITLISTED`。

全部通过后：

```text
promotion_offer: PENDING → ACCEPTED
registration_cycle: WAITLISTED → CONFIRMED
```

两个状态与审计记录在同一个事务中更新。

### 拒绝邀请

用户拒绝后：

```text
promotion_offer: PENDING → DECLINED
registration_cycle: WAITLISTED → PROMOTION_DECLINED
```

如果是先到先得岗位，系统继续邀请下一位候补者。

### 邀请过期

定时任务默认每 30 秒执行一次，但不会暴力扫描整张表。SQL 只查询：

```sql
WHERE status = 'PENDING'
  AND expires_at <= 当前数据库时间
ORDER BY expires_at, id
LIMIT 100
```

它只先读取一小批到期 ID，不在扫描阶段持有行锁。随后每个 ID 交给独立的 `REQUIRES_NEW` 事务处理，重新按成员、岗位、周期、邀请顺序加锁并检查状态。

过期后：

```text
promotion_offer: PENDING → EXPIRED
registration_cycle: WAITLISTED → PROMOTION_EXPIRED
```

先到先得岗位继续递补下一人。

### 为什么前端倒计时不能决定过期

用户可能修改本机时间。前端倒计时只用于展示；真正的有效性由数据库当前时间和后端事务判断。倒计时归零后，前端重新请求服务器状态，而不是在本地直接修改报名状态。

### 关键源码

- 接受与拒绝：`backend/src/main/java/com/volunteerflow/registration/PromotionService.java`
- 分批扫描：`backend/src/main/java/com/volunteerflow/registration/PromotionExpiryJob.java`
- 单邀请过期事务：`backend/src/main/java/com/volunteerflow/registration/PromotionExpiryService.java`

## 十二、Redis 和 Kafka 为什么没有放进报名主事务

### 讲述稿

如果一开始用 Redis 扣库存、MySQL 写报名，就必须解决缓存成功但数据库失败、数据库成功但缓存失败、锁租约过期和故障降级等问题。当前先使用 MySQL 建立可证明的正确性基线，后续通过压测确定瓶颈后，Redis 可以用于缓存、限流或分布式辅助锁，但数据库唯一约束和事务仍保留。

Kafka 当前还没有进入主链路。未来通知异步化时会使用 Transactional Outbox：业务事务只写数据库报名结果和 Outbox 事件，独立发布器将事件发送到 Kafka。即使 Kafka 暂时不可用，用户仍能报名，恢复后再补发通知。

## 十三、现场演示顺序与讲解词

### 演示前准备

准备以下账号和数据：

- `owner`：组织负责人；
- `manager`：活动管理员；
- 至少两个普通成员；
- 一个容量为 1 的先到先得岗位；
- 一个需要人工审核的岗位；
- 报名时间窗口覆盖演示时间。

### 第一步：登录

操作：使用普通成员账号登录。

讲解：

> 登录成功后，Access Token 只保存在前端内存，Refresh Token 通过 HttpOnly Cookie 保存。普通接口携带短期 JWT，过期后前端只发起一次刷新并重放原请求。

### 第二步：查看活动和岗位

操作：进入活动详情，切换不同岗位。

讲解：

> 容量和报名模式属于岗位。选择岗位后，系统将活动公共问题和岗位专属问题组合成报名表。

### 第三步：第一个成员报名

操作：报名容量为 1 的先到先得岗位。

预期：状态为“已录取”。

讲解：

> 后端先锁成员再锁岗位。因为当前占用数小于容量，所以周期状态直接变为 CONFIRMED。

### 第四步：第二个成员报名

操作：换第二个账号报名同一岗位。

预期：状态为“候补中”，显示原始候补序号和当前位次。

讲解：

> 岗位已经满员，所以新周期进入 WAITLISTED。候补序号从岗位行中分配，岗位锁和唯一约束防止并发重复序号。

### 第五步：正式成员取消

操作：第一个成员取消报名。

预期：第一名候补获得限时邀请。

讲解：

> 取消和创建递补邀请在同一个事务中完成。邀请为候补者预留名额，因此 PENDING 邀请也计入容量。

### 第六步：候补接受邀请

操作：第二个成员打开报名状态页，展示倒计时并点击“接受递补”。

预期：邀请变为 `ACCEPTED`，报名周期变为 `CONFIRMED`。

讲解：

> 前端倒计时只负责显示，后端使用数据库时间重新检查邀请是否仍有效。邀请和报名周期在一个事务中更新，重复点击会因为状态已变化而返回冲突。

### 第七步：展示管理端

操作：用 manager 查看审核页面，用 owner 查看组织管理和角色分配。

讲解：

> manager 负责活动运营和报名审核，owner 额外负责角色与权限。权限最终由 Service 层 RBAC 校验，前端隐藏按钮只是体验优化。

## 高频追问与参考回答

### 1. 为什么不用消息队列做递补？

递补直接影响名额正确性，当前将它与取消放在同一个本地事务中保证强一致性。消息队列适合通知等允许最终一致的业务。

### 2. 如果用户连续点击报名会怎样？

前端提交期间禁用按钮，但这不是最终保证。后端通过成员锁、活动用户唯一约束、有效周期检查和重复键异常转换，确保只产生一个有效报名结果。

### 3. 如果用户同时接受邀请和取消报名呢？

两个流程使用相同的成员、岗位、周期、邀请锁顺序，而且加锁后会重新检查状态。不会产生一边取消一边确认的矛盾结果。

### 4. 为什么使用数据库时间？

应用可能部署多个实例，机器时间可能存在偏差，用户也可以修改浏览器时间。容量预留、邀请过期和迟取消都以数据库时间为准，确保所有事务共享同一时间基准。

### 5. 为什么没有物理外键？

项目遵循约定，不使用物理外键和级联操作，而是在 Service 事务中检查资源存在性、状态、组织归属和删除保护。这样跨模块演进更灵活。但唯一约束和普通索引仍然保留，因为它们承担并发唯一性和查询性能职责。

### 6. 为什么选择模块化单体？

当前流量规模下，核心难点是报名事务正确性。模块化单体既能按领域隔离代码，又能使用本地事务保证报名、递补和审计原子性。过早拆微服务会增加网络失败、分布式事务、消息可靠性和部署成本。

### 7. manager 和 owner 有什么区别？

manager 负责日常活动运营，包括创建活动、审核、递补和签到；owner 在此基础上还可以管理组织成员的角色并且，OWNER 是受保护角色，并自动拥有未来新增的组织权限。

### 8. 当前项目最需要继续完善什么？

第一是完成权限感知的前端菜单，避免无权限的用户看到管理按钮；

第二是完成通知以及签到的链路；

第三是进行测试并记录真实延迟；

第四是引入 Outbox 和 Kafka 做可靠异步通知。
